Задача №1. Техническая инфраструктура

Как я работаю с технической частью сайтов

Если веду два магазина — на 1С-Битрикс и на другой CMS — у меня один порядок: понять задачу и риски, сделать в git-ветке, проверить на локали и staging, выложить, после релиза посмотреть логи и ключевые сценарии. Ниже — как именно решаю типовые задачи.

Добавление нового функционала на сайт

1. Уточняю сценарий: кто пользуется, какие сущности меняются, что нельзя сломать в заказе, кабинете и обменах.
2. Оцениваю, хватает ли штатного механизма CMS.
3. На Битрикс путь такой: local/modules или local/components, обработчики событий через EventManager, при необходимости HL-блок или свойства инфоблока, миграции структуры через мигратор или sql/admin-скрипт, выкладка через git на staging, потом на прод.
4. На другой CMS: плагин/модуль, хуки темы, отдельный сервисный класс вне шаблона, миграция БД средствами CMS или Phinx/Doctrine Migrations, тот же контур ветка → staging → prod.
5. После релиза проверяю целевой сценарий вручную и смотрю error.log / журнал CMS.

Доработка каталога товаров, фильтров и поиска

1. Смотрю текущую схему свойств, индексы БД и как строится выборка сейчас.
2. На Битрикс: настраиваю свойства инфоблока под фильтр, пересобираю фасетный индекс умного фильтра, проверяю ЧПУ и SEO-шаблоны фильтрованных URL, при тормозах профилирую компонент каталога и кеш.
3. На другой CMS: правлю атрибуты/таксономии каталога, индексы MySQL по фильтрам, если встроенного поиска мало — выношу поиск в Elasticsearch/OpenSearch с отдельной индексацией товаров.
4. Проверяю: релевантность, пустую выдачу, мобильную вёрстку фильтра и время ответа на крупных разделах.

Интеграция сайта с 1С и сторонними сервисами через API

1. Для 1С фиксирую протокол обмена: сущности, направление, расписание, внешние идентификаторы, поведение при частичной ошибке.
2. На Битрикс обычно иду через штатный обмен CommerceML / REST, а кастом дописываю агентами или очередью (Bitrix\Main\ORM + таблица заданий / RabbitMQ, если объём большой). Логи обмена храню отдельно, без паролей.
3. Для сторонних API делаю отдельный клиент: timeout, retry с ограничением, идемпотентный ключ, запись статуса синхронизации в БД.
4. На другой CMS то же самое через cron-воркер или очередь (Redis/Rabbit), webhook endpoint с проверкой подписи.
5. Перед боем прогоняю обмен на staging на копии данных и смотрю дубли, пропуски и время полного цикла.

Оптимизация скорости загрузки сайта

1. Снимаю baseline: TTFB, LCP, вес HTML/CSS/JS, число запросов, slow query log.
2. Режу тяжёлое по порядку: изображения (WebP/AVIF, размеры), отложенная загрузка медиа, минификация и объединение ассетов где уместно, CDN, gzip/brotli.
3. На Битрикс включаю и проверяю композит, автокеш компонентов, чищу лишние подключения ядра на публичных страницах.
4. На другой CMS настраиваю full-page/object cache, убираю тяжёлые плагины с витрины, выношу статику на CDN.
5. После изменений снова меряю те же URL и сценарии каталог → карточка → корзина.

Исправление ошибок в программном коде

1. Воспроизвожу баг на том же окружении и данных.
2. Смотрю stack trace, access/error log, журнал CMS, при необходимости xdebug/profiler.
3. Делаю минимальный фикс в отдельной ветке.
4. Добавляю регрессионный тест или хотя бы чеклист сценария, на котором падало.
5. Если ошибка на боевых данных или в обмене — сначала staging, потом прод. В релиз только понятный патч с описанием причины.

Разработка новых страниц и разделов

1. Определяю тип страницы: контент, посадочная, сервисная, коммерческая.
2. На Битрикс создаю раздел в структуре сайта, подключаю комплексный компонент или local-компонент, заполняю SEO-поля, подключаю стили через Asset или шаблон сайта.
3. На другой CMS делаю шаблон страницы/типа записи в теме либо блок конструктора, если проект на нём сидит.
4. Перед публикацией проверяю адаптив, индексацию, микроразметку при необходимости и отправку форм.

Настройка резервного копирования и обеспечение безопасности

1. Бэкапы: ежедневный дамп MySQL + архив файлов/uploads, хранение минимум 7–14 дней вне боевого сервера, раз в период делаю пробное восстановление на отдельном стенде.
2. Безопасность: HTTPS, обновления ядра и модулей, минимальные права на файлы и БД, закрытие служебных URL, защита админки (IP/2FA где возможно), валидация загрузок, секреты только в env/конфиге вне webroot.
3. Мониторинг: доступность, место на диске, успешность бэкапов, error rate после релизов.

Итого: на Битрикс и на другой CMS я решаю задачи через конкретный технический путь платформы, но с одним контуром контроля — ветка, проверка, релиз, наблюдение после выкладки.
